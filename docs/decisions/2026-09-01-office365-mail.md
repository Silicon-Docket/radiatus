# Linking Office 365 mail to customers: deep link, not a Graph integration

**Date:** 2026-09-01
**Status:** Superseded &mdash; see [docs/office365-mail-setup.md](../office365-mail-setup.md)

> **Superseded 2026-09-01.** The premise of what shipped here turned out to be
> false: checked in a real browser, Outlook Web does not represent search state
> in the URL at all, so there is no deep link to build on — running a search
> leaves the address bar with no query in it. The deep link and its copy-address
> fallback have been removed.
>
> What replaced it is exactly the shape this record's "If this is revisited"
> section describes: `src/graph.js` + `GET /api/mail/lookup`, metadata only, one
> mailbox from `env.GRAPH_MAILBOX`, access granted via Exchange RBAC
> (`Application Mail.ReadBasic`) with no `Mail.*` consent in Entra, and each row
> linking out via `webLink`. Both unknowns listed below remain unverified
> against a live tenant, and are restated in the setup doc.
>
> Everything below is left as written. The reasoning about Entra consent
> unioning with Exchange RBAC, and about what `ADMIN_API_TOKEN` is and is not a
> reasonable gate for, is why the replacement is scoped the way it is.

## What we wanted

From the customer view in `/admin`, see the email correspondence with that
customer, sourced from Office 365.

## What we built

A link. The customer's address renders as a one-click Outlook web search,
plus a copy-to-clipboard fallback. ~20 lines in `ADMIN_HTML`, no new route,
no new secret, no new binding, no setup steps for anyone deploying this
template.

## Why not a real Microsoft Graph integration

We researched it properly before deciding. The blockers are not technical
difficulty — the integration is buildable in ~200 lines — they are what it
costs the people who deploy this template.

**The permission is tenant-wide by default.** Graph's application permission
`Mail.Read` is documented as "read mail in all mailboxes without a signed-in
user". Narrowing it to a single mailbox requires Exchange RBAC for
Applications, configured through Exchange Online PowerShell.

**The narrowing fails silently.** If an adopter configures the Exchange RBAC
scope *and also* clicks "Grant admin consent" in Entra — the step muscle
memory reaches for — the two grants union, the scope stops constraining
anything, and everything still appears to work. There is no error state that
tells them their mail access is unscoped.

**The setup cost is disproportionate.** Roughly eleven manual steps across
two admin consoles: an Entra app registration, a client secret that expires
within 24 months and will silently break the deployment, a Global
Administrator (usually not the person deploying), a local PowerShell module
install, a mail-enabled security group, three cmdlets, and a 30-minute to
2-hour cache wait before you can tell whether any of it worked. None of it
can be automated by the template. Today's entire setup is `wrangler login`,
`d1 create`, two `secret put`s, and a deploy.

**The gate doesn't justify the data.** `/api/*` is protected by
`ADMIN_API_TOKEN`: a single shared string, pasted into a browser field by
every support person, with no per-operator identity, no rotation story, and
no record of who searched which mailbox. That is a reasonable gate for
read-only Stripe billing metadata. It is not a reasonable gate for other
people's email — and Exchange's own `MailItemsAccessed` audit record is
enabled by default only on E3/E5 licenses, which the median adopter of a
small open-source Stripe CRM will not have. So for many adopters there would
be no record on either side.

**A template README is a script people follow without thinking.** If the
fastest path through that script ends at "Grant admin consent", this project
would industrialise over-permissioning across every tenant that adopts it.
That is a worse outcome than not shipping the feature.

## What the deep link gives up

No thread count or subject list in the page — no "3 threads, last reply 2
days ago" at a glance, and no way to confirm a reply exists without leaving
the app. The operator switches to Outlook.

In exchange, each operator sees exactly the mail they are already entitled to
see, authenticated as themselves, logged under their own identity. That
attribution property is the thing a server-side app-only integration
destroys, and it is worth more here than the tab switch costs.

## If this is revisited

The defensible integrated shape — should someone want it in a fork — is
metadata only: Exchange RBAC granting `Application Mail.ReadBasic` scoped to
a single shared support mailbox, with no `Mail.*` permission consented in
Entra at all, message bodies excluded *by the grant* rather than by our code,
and each row linking out via the message's `webLink` so Outlook remains the
reader. Two things must be verified against a live tenant first, because the
documentation does not settle them:

1. Whether a client-credentials token with zero Entra `Mail.*` consent is
   actually accepted for `/users/{mailbox}/messages` when access comes only
   from Exchange RBAC. The migration docs imply yes; Microsoft never states
   it normatively.
2. Whether `$search` works under `Mail.ReadBasic`. If it does not, the
   fallback filters on sender only — you could show what the customer sent
   you, but not what you replied.

It should not ship in the base template's Quick Start either way.

## Caveat on what we did ship

The Outlook deeplink URL shape
(`outlook.office.com/mail/deeplink/search?query=`) is community-reported, not
documented by Microsoft, so it may break without notice. That is why the copy
button sits next to it as a guaranteed-working fallback.
